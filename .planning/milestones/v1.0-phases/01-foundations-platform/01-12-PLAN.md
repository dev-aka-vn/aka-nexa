<objective>
Close UAT gaps G2 and G3: the onboarding documentation names the system's real error tokens and boot-failure modes, and the onboarding spec passes or fails only for reasons that have to do with the property under test.

Purpose: `01-11` delivered G1's artifacts — `.env.example`, `compose.dev.yml`, `README.md`, `tooling/onboarding.spec.ts`, a `.gitignore` entry — and then a post-execution code review found that the new documentation asserts three things that are false about the system's own behaviour, and that the acceptance spec fails 4 of 27 on the machine's normal state while being able to pass against a foreign process. Both are the fourth instance of this phase's recurring defect: something in a document (or a test) asserts a property nothing verifies.

G2's fix is therefore not only correcting prose. Correcting prose with nothing asserting it reproduces the identical defect one cycle later. Every corrected token below is derived by invoking the code that emits it, in the same assertion that requires the documentation to contain it. The two claims that have no mechanical reduction are named as prose, with the reason, and routed to a `<human-check>` rather than left ambiguous.

G3's fix is to remove the machine from the spec's outcome. Nothing in `tooling/onboarding.spec.ts` will bind or depend on the host's api default port after this plan, so the file's result is the same whether or not something else holds it — which is the state this machine is in right now.

Output: corrected `.env.example` and `README.md`, and a `tooling/onboarding.spec.ts` that decides every claim it documents and cannot be satisfied by a foreign process.

</objective>

<decisions>
The orchestrator asked for each G2 claim to be classified — assertion, or prose with the reason — and for the WINDOWS #18 budget question to be answered deliberately rather than by widening a number until something goes green. Both are answered here, before the tasks, so the executor is not left to improvise either.

**D-1 — Correction alone is not the deliverable; derivation is.** All four G2 claims are assertion-backed. The derivation is not a second copy of the token, it is the token: each assertion calls the emitter and requires the caught message to appear in the documentation. If the emitter changes, the assertion changes with it and the documentation has to follow; if the documentation drifts, the assertion is red. This is the `toolchain-pin.spec.ts` idiom (`.nvmrc` ↔ `engines.node` agree) applied to error strings, and it is the only construction under which a corrected sentence stays corrected.

**D-2 — Two sub-claims stay prose, and this is stated rather than left ambiguous.** (a) *Which* failure mode each token belongs to — the attribution sentences in the README's token table. There is no mechanical reduction for "this row is correctly labelled": a table can satisfy every derived-token assertion above and still swap two rows, and a phrase-match on "unset" versus "absent" is the brittle test `01-11`'s plan explicitly forbade ("a brittle phrase-match is a test that fails on a good edit and asserts nothing on a bad one"). (b) Whether the README's framing of the `NODE_ENV` warning reads as a warning rather than as reassurance. Both are routed to Task 1's `<human-check>` and recorded in the SUMMARY. Everything *around* the attribution is asserted: the token is derived, the ENOENT is reproduced, and the documented remedy is executed and accepted.

**D-3 — The README's install claim is corrected in prose, not made true in the manifest.** G2 offers two routes: state that npm warns, or add `engine-strict` so the claim becomes true. This plan takes the first. `engine-strict` would be a new file outside `files_modified`, and it changes install behaviour for every developer and every CI job — a toolchain decision, not a documentation correction. Choosing it here would be the plan quietly widening its own scope. The corrected sentence is instead pinned by an assertion: no `.npmrc` in the repository sets `engine-strict`, and adding one turns the README red. That is the direction that matters — the document cannot claim an enforcement the repository does not have.

**D-4 — G2's structural alternative is surfaced, not silently declined.** `NODE_ENV=development` being *active* in a file a deployment might copy is the underlying risk. The stronger remedy is to comment `NODE_ENV` out, exactly as `SERVICE_NAME` is commented out, so the local boot fails closed and an operator must state their environment deliberately. That change alters the documented boot contract, so it is not a documentation fix and this plan does not make it. It is Task 1's second `<human-check>` question.

    The decision-maker is handed the cost picture, because two of this plan's own assertions move and neither is obvious. Measured, not inferred: `namedValidate` in `config.module.ts:34` — like `validateConfig` — formats only `result.error.issues[0]`, and `NODE_ENV` is declared before `SERVICE_NAME` in `AppConfigShape` (`config.schema.ts:64` and `:68`). So with both absent the boot reports the *first* missing key, which becomes `NODE_ENV`. Three things follow, and all three must be decided together rather than one at a time:

    - The **existing green assertion** at `tooling/onboarding.spec.ts:592` — "refuses the same file unmodified with a named `CONFIG_INVALID: SERVICE_NAME`" — goes red. Its premise is that the shipped file misses exactly one required key, and that premise is load-bearing.
    - The **existing green assertion** "keeps `NODE_ENV` active, never a comment (T-1-27)" must be removed or inverted. `T-1-27`'s mitigation is written against an active `NODE_ENV`, so the threat row moves with it.
    - **Case 6's premise disappears.** It reproduces the sourcing overwrite, which only exists while `NODE_ENV` is an active line. The two legitimate responses are to remove Case 6 with D-4's decision recorded in the SUMMARY, or to invert it into an assertion that sourcing no longer rewrites the variable. What is *not* legitimate is leaving it asserting a hazard the file no longer has.

    What is delivered unconditionally is the disclosure — both documents name `NODE_ENV` as the guard's switch — so the risk is documented either way, and the operator can take the structural route with a full account of what it costs.

**D-5 — WINDOWS #18: the budget is widened deliberately, to a number that already exists in this repository.** The Task 2 documented-path shell command probes `/health/ready` for 30 × 500 ms = 15 s. On this host the same boot needs ~29 s, and the executor recorded the failure rather than editing the command — correct, and this plan does not repeat it by nudging a number until a run goes green. The new budget is **120 × 500 ms = 60 s**, which is the budget `bootUntilLive` in `tooling/onboarding.spec.ts` already uses for the *same boot*. The derivation is therefore "one boot, one budget, taken from a constant already in the repo", not "the failing run took 28.8 s, so 40 s would do". The choice between WINDOWS #18's two offered routes — re-run on an idle host, or widen `N` deliberately — is the second, and this is that decision.

    Entry 18 also under-records G3, and the orchestrator should widen it rather than close it. As written it says only that the probe budget is host-dependent, which reads as settled; the load-bearing half of G3 is that on a busy port the **spec** failed 4 of 27 outright, which entry 18 does not mention at all. `.planning/WINDOWS.md` is outside this plan's `files_modified`, so the row is the orchestrator's to amend — carry this text into the SUMMARY verbatim so nothing is paraphrased away: *"the probe budget is 30×500ms (15s) and external load stretches Nest+instrumented-driver module load to ~29s; the budget is now 120×500ms (60s), matching `bootUntilLive` in `tooling/onboarding.spec.ts` for the same boot — widened deliberately as a planning decision, not fitted to the failing run. Separately and more seriously: when the api default port was occupied, `tooling/onboarding.spec.ts` failed 4 of 27 with `EADDRINUSE` and could pass against a foreign process on the port. Both are addressed by gap G3's closure: every boot in the spec now acquires and proves its own port, and the responder is proved to be the process under test."*

**D-6 — The documented-path command keeps the default port, and gains a bind precondition instead.** It boots the api the way a reader does, on `DEFAULT_PORT_BY_SERVICE.api`, so moving it to an acquired port would stop it being a check of the documented path. What it gains is a separate probe that runs first and reports `PORT_OCCUPIED` with the occupant named and the remedy quoted — so a busy host produces a diagnosis instead of a 60-second `NOT_READY`. That is the same property G3 asks of the spec, expressed in the one place the spec cannot reach.

**D-7 — What G3 gives up, stated plainly.** After Task 2 no test binds the derived default port, so the link "`SERVICE_NAME=api` with no `PORT` ⇒ `app.listen(3000)`" is no longer proven by a live bind in this file. Stated precisely because the coverage is not as general as it looks: that spec's loop is a literal list, not a walk of `SERVICE_NAMES`, so a fourth service added to the enum would not be covered there — which is a gap in *that* spec and not something this plan creates or is asked to close. The alternative — keeping one derived-default boot — makes the whole file's result depend on whether the host's 3000 is free, which is the defect G3 exists to close, and a test whose precondition is a property of the machine is a false-red generator. The trade is deliberate and recorded.

**D-8 — `01-11`'s six prohibitions stay live on the files this plan edits.** That plan marked all six `resolved`, and this plan touches three of the five files they constrain, so they are carried forward rather than left to a prior document: no secret value in `.env.example`; no `CRYPTO_LOCAL_KEY_ALLOWED` anywhere in it; `NODE_ENV` stays an **active** line and `CRYPTO_KEY_PROVIDER=local` stays development-labelled; no compose published port may leave loopback; no `?directConnection=true` in the documented `MONGO_URL`; and the README must keep reading as a development convenience rather than a deployment topology. The last of these is the one this plan is most likely to disturb — D-4 adds security framing next to the sourcing recipe, and framing is exactly what `01-11`'s own P5 could not decide mechanically — so it is repeated in Task 1's `<human-check>`.

  <action>
    This task corrects four claims in two documents and adds one container-free describe block to the spec that decides all four. It is one concern: the documentation's statements about the system's own failure modes.

    **The derivation rule, which is the whole task.** Every token this task puts into a document is first read out of the code that emits it, inside the same assertion that requires the document to contain it. If you find yourself typing a token into an `expect(...).toContain(...)` call as a string literal, that is the defect this task exists to remove — the token must come from a caught exception. 01-11 wrote the documentation from the *intent* of each guard; the intent is not what a reader greps for.

    **New describe block: `documented error tokens and guard triggers — derived from the code that emits them`.** Container-free and process-free; it must not call `startThreeContainers`, must not spawn the api, and must complete in seconds. Each case below is one assertion or one tight pair.

    *Case 1 — the D-12 refusal token.* Call `validateConfig` (import from `@akane/platform`) with a complete, otherwise-valid config in which `REDIS_CACHE_URL` and `REDIS_QUEUE_URL` are byte-identical. Catch the thrown error. Assert the caught message equals the greppable form `CONFIG_INVALID: <root> REDIS_INSTANCES_NOT_DISTINCT` — this pins the derivation itself, so if `formatConfigError` ever changes its rendering the failure says so here rather than as a confusing "document missing token".
