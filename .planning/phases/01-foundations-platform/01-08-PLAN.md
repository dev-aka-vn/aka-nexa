## Phase Goal

> Same derivation as plan 01: the ROADMAP goal is not in user-story format, so it is restated, not invented. **As a** platform engineer, **I want to** register long-running scheduled work through BullMQ Job Schedulers with one metrics path, **so that** a task registered once runs on every replica without leader election, and queue state cannot silently scatter across cluster slots.

<objective>
Build the async-execution floor. Ship the BullMQ queue module with the `{akane-q}` hash-tag prefix and
the two connection profiles, the idempotent `upsertJobScheduler` registration used for
`platform-heartbeat`, the worker and scheduler readiness indicators, and business-metric instrument
registration through `@opentelemetry/api`. Do not add a scheduler listener loop, a DLQ policy, or any
connector behaviour — those are later phases.

Purpose: FND-08 requires that a task registered once runs on every replica, and BullMQ 6's
`upsertJobScheduler` is that primitive. D-14's prefix and connection-profile split decide where every
live queue key lives and how a request-path producer fails when Redis is down — both are hard to
change once jobs are in flight. OBS-01 requires the metric instruments to come from the OTel meter, not
a second `prom-client` registry.

Output: a queue module, a proven-idempotent Job Scheduler registration, two readiness indicators, and
the OTel meter instrument registration.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| replica → shared queue | Every replica registers the same scheduler; a non-idempotent registration would multiply scheduled work. |
| producer (HTTP path) → Redis | A hanging producer turns a Redis outage into a hung request, not a fast failure. |
| worker → Redis blocking read | A blocking connection with a finite retry setting makes BullMQ throw. |
| metric instruments → scrape endpoint | A second registry would produce split alert rules. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-19 | Denial of Service | `queue.module.ts` / `queue.provider.ts` | high | mitigate | Worker blocking connection sets `maxRetriesPerRequest: null` (BullMQ requires it); producers set 1–3 so the request path fails fast instead of hanging (D-14). |
| T-1-20 | Tampering | queue key layout | medium | mitigate | All queue keys carry the `{akane-q}` hash tag so they occupy one cluster slot, and no client sets `keyPrefix` — two disagreeing prefix layers cannot arise (D-14). |
| T-1-SC | Tampering | npm installs | high | mitigate | `bullmq@6.3.11`, `@nestjs/bullmq@12.0.0`, `ioredis@6.0.0`, and `@opentelemetry/api@1.9.1` are carried in `STACK.md §14`; no unpinned install. |
