## Phase Goal

> Same derivation as plan 01: the ROADMAP goal is not in user-story format, so it is restated, not invented. **As a** platform operator, **I want to** have OTel traces with a frozen attribute allowlist and one Prometheus metric path, **so that** the trace backend never accumulates a correlatable submission map, and there is a single metrics endpoint to alert on.

<objective>
Wire observability so the trace backend can never correlate back to a submission. Ship the frozen
span-attribute allowlist, the wrapping `AllowlistSpanExporter`, the `NodeSDK` bootstrap with the OTLP
trace and metrics exporters plus the Prometheus exporter, and the single `/metrics` route served from
the app. Keep the exporter instance a singleton so the metric instruments registered in plan 08 land on
exactly one scrape endpoint.

Purpose: FND-07 and D-18 are irreversible — the trace backend has no per-app RBAC and no erasure path,
so whatever attributes are exported stay exported. OBS-01 forbids a second metric path; wiring the
Prometheus exporter here (not `prom-client`) is what makes that true.

Output: a filtered trace exporter, an OTel-first bootstrap function, and one `/metrics` endpoint.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app process → trace backend | Whatever attributes leave the process are retained by a store with no per-app RBAC and no erasure path. |
| metric instruments → scrape endpoint | A second registry or server creates split alert rules and an unmanaged surface. |
| external scraper → `/metrics` | The scrape route is an unauthenticated read of operational state. |
