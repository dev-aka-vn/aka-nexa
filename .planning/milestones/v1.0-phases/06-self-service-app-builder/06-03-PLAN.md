<objective>
Deliver IDN-05: an employee with no CSV mapping self-onboards by verifying an OTP sent through their IM account — 10-minute expiry, 3 attempts, 30-minute lockout — over a Redis-backed state machine wired into the chat pipeline's inbound-event processor.

Output: the OTP state machine, the onboarding service, the chat-pipeline delivery port, the inbound-processor wiring, and the Zod contracts. The live Slack delivery leg is a manual-verify item (06-VALIDATION.md: "Manual Slack OTP leg in staging; state machine itself is integration-tested").
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-10 | Tampering | OTP brute force | high | mitigate | 3-attempt limit with Redis INCR (atomic across instances) + 30-minute lockout from the third failure (IDN-05); codes are 6-digit with a per-identity key namespace; the spec proves a 4th attempt is refused |
| T-06-11 | Information Disclosure | OTP misdelivery | high | mitigate | The OTP is delivered only to the chat identity that requested it (OtpDeliveryPort.deliverOtp(chatUserId, code) — the port's single parameter is the requesting identity); a code requested by identity A never verifies for identity B (per-identity key namespace, spec-asserted) |
| T-06-12 | Tampering | OTP replay | medium | mitigate | Single-use codes: successful verify deletes the key and leaves a consumed tombstone; replay is refused with OTP_CONSUMED (spec-asserted) |
| T-06-13 | Information Disclosure | plaintext OTP at rest | medium | mitigate | Only the SHA-256 hash of the code is stored in Redis; the plaintext exists solely in the in-memory delivery-port call (spec asserts no plaintext in the Redis record) |
