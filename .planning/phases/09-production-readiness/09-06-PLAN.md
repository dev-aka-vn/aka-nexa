<objective>
Close WINDOW 7 by making key material rotatable without downtime and proving it: the additive wrapped-DEK fix in the envelope, a keyring that resolves by `kid` on both the envelope and JWT paths, a re-wrap path, an operator CLI command, and a rotation runbook.

Purpose: This is the zero-downtime key rotation item ROADMAP Phase 9 names as verified here, and it closes the last open compliance blocker in the broken-windows ledger (row 7: "no real credential may be stored before it"). Without it, rotating a key makes previously sealed envelopes undecryptable, which means the platform has no rotation capability at all.
Output: The envelope amendment, two rotation specs, a rotation CLI, and a key-rotation runbook.

Dependency: this plan is wave 2 because the runbook set created in plan 09-03 establishes the `docs/runbooks/` directory and the alert-to-runbook index. This plan adds the sixth runbook and the index row for it.

WINDOW 7's row explicitly states the upgrade is **additive**: "the five envelope fields do not change". The fix is to persist a per-secret wrapped DEK beside the existing five fields via a sibling field on the stored record — not to change `SecretEnvelope`, which is frozen at five fields by D-25. Read the envelope's header comment before touching it; it documents this upgrade path precisely.

Prohibited pattern (Pitfall R7 and the ledger's own wording): restarting the process and observing traffic succeed proves nothing about rotation. The proof must be a decrypt surviving a rotation boundary under concurrent traffic.
</objective>

    Add the concurrency case to `envelope-rotation.spec.ts`. The shape that proves rotation under traffic: start a stream of decrypt operations against records sealed under the retired kid, perform the rotation (promote B to active) while the stream is running, and assert every operation in the stream succeeded and none observed a failure or a fallback. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| key provider -> envelope and JWT verification | The keyring decides whether a ciphertext or token is trusted; a fallback here silently accepts material signed under a retired key. |
| operator CLI -> keyring | The rotation command mutates the key material every sealed secret and every issued token depends on. |
| stored secret record -> decrypt | The sibling wrapped-DEK field is new persisted material whose integrity decides whether a ciphertext opens. |

## STRIDE Threat Register

ASVS level 1 (`security_asvs_level: 1`, `security_block_on: high`).

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-34 | Spoofing | `decryptSecret` kid resolution | high | mitigate | An absent kid throws `KEY_ID_MISMATCH` and never falls back to the active key; a fallback would accept material sealed under a retired or attacker-chosen key. Asserted by a spec with only a different kid present. |
| T-09-35 | Tampering | Sibling wrapped-DEK field | high | mitigate | The wrapped DEK is unwrapped only through the provider's authenticated wrap/unwrap path and the envelope's auth tag still gates the plaintext; a spec asserts a tampered ciphertext under a valid kid fails authentication. |
| T-09-36 | Elevation of privilege | JWT verifier keyring | high | mitigate | The verifier resolves keys from the same keyring as the envelope path and rejects a removed kid without fallback; the pre-existing "unknown kid must not fall back" rule is preserved and extended to rotation. |
| T-09-37 | Denial of service | Rotation without an overlap period | high | mitigate | The previous kid is retained for a stated overlap period and the CLI reports the expiry; removing it immediately would make every in-flight envelope and token undecryptable during a rolling deploy. |
| T-09-38 | Repudiation | Rotation CLI outcome | medium | mitigate | A no-op is reported as already-active distinct from a successful promotion, and an unknown kid exits non-zero; an operator cannot mistake an unchanged keyring for a rotation. |
| T-09-39 | Tampering | Nonce uniqueness under a new key | high | mitigate | A fresh random 12-byte iv per encryption is preserved — the pre-existing iv-uniqueness spec still passes — because a per-secret DEK changes the key but not the nonce-reuse hazard. |
| T-09-40 | Denial of service | Rotation verification cost | low | accept | The concurrency harness runs in-process against a local provider at test scope; it adds no production path and needs no further control. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no new package; `jose` is already a runtime dependency and the existing crypto stack is unchanged. |
</threat_model>
