**Project:** aka-nexa — IM-Driven App Builder & Integration Gateway
**Domain:** Enterprise chat-driven workflow gateway (IM adapters → permission-first routing → signed one-time links → FormIO.js forms → hybrid data routing)

## Executive Summary

aka-nexa v1 shipped a chat front-door: a user types a request in Slack or Teams, a permission-first routing pipeline picks an app, and the platform replies with a signed link to a FormIO.js form. **v2 does not extend that loop — it completes it.** The three independent research passes converge on a single, uncomfortable headline: **the outbound half of the product does not exist.** `InboundEventProcessor.process()` returns `{kind:'link', appId, url}` and BullMQ discards a processor's return value; `TeamsOutboundService` has no caller anywhere in the repo; the only working outbound path is the notification queue, and it hardcodes `TeamsDeliveryService`. A Zalo adapter built on top of that produces a bot that reads messages perfectly and answers nothing. The second headline is equally load-bearing: **`RbacService.hasPermission` returns `true` unconditionally**, `perm_version` defaults to `0`, the RBAC cache is an in-process `Map`, and the identity mapping is an in-memory array. That is a v1 correctness defect, not a v2 feature — and group-based RBAC plus a permission-first AI guard are both meaningless on top of it. So the recommended approach is **foundations-first**: build the outbound delivery seam, replace the stub authoriser with a real epoch-backed RBAC over persistent state, amend the event envelopes with *optional* threading and native-event-id fields, then add Zalo and Telegram as two-sided plug-ins on top of that shared substrate.

The second research theme is that **v2's new capabilities collide with surfaces that v1 deliberately froze**, and the correct answer in every case is *do not touch the frozen set, express the new behaviour around it*. D-21 (read-link claims) must not gain a group claim — group revocation is folded into the existing `perm_version` integer by bumping a stored, monotonic per-`(user, app)` epoch. D-23 (JEV v1 wire) must not gain a `guard` field — the AI guard is a `JevProvider` **decorator**, not a pipeline stage, so it inherits the deadline, the attempt cap, the health probe, the confidence gate and the `canOpenNow` re-check for free. D-16/D-18 (log and span allowlists) are *widened deliberately*, with a written justification in the same commit — the friction is the control. The only frozen-set change v2 needs is on the **event envelopes**, which are `.strict()` but not frozen: two optional threading fields and one `native_event_id` are backward-compatible and require no spec-version bump.

The third theme is platform reality, and it is where the risk concentrates. **Zalo OA has no official Node SDK** — every npm candidate is deprecated, unlicensed, or an unofficial *personal-account* reverse-engineering library (`zca-js`, 168K weekly downloads, whose own README warns accounts "can be locked or banned"), so a hand-rolled `undici` client is the only defensible choice. Zalo's webhook signature is a **plain SHA-256 concatenation, not an HMAC**, computed over the exact raw bytes with the *OA* Secret Key — three independent ways to get it wrong, each producing an indistinguishable 401. Its 2-second ack budget is tighter than Slack's 3 seconds and its failure mode is worse: after five retries Zalo **silently disables the webhook**, and re-enrolment is a manual portal action. Its access token lives 25 hours and its refresh token is a **single-use rotating 90-day credential** — a crown jewel, not a renewable token. Its identifiers are 19 digits, beyond `Number.MAX_SAFE_INTEGER`, so `JSON.parse` silently merges two users into one identity. And Zalo only returns full user profile data to a **Vietnam-region egress**, which collides head-on with the platform's region-locked data-residency constraint. Telegram is the opposite: a first-party SDK with thorough docs (`node-telegram-bot-api@2.1.0`, zero runtime dependencies, ESM, uses global `fetch` so OTel traces stay continuous), but with its own traps — `callback_data` capped at **64 bytes** where exceeding it fails the whole message, commands that carry **no scope information** (Telegram says so explicitly), privacy mode that hides most group traffic, and a Bot API with **no member enumeration at all**, which means Telegram group→role sync is simply not implementable. Mitigation throughout: three new runtime dependencies total, two-day spikes against real accounts, and a phase order that puts the low-risk adapter before the high-risk one.

## Key Findings

### Recommended Stack

The v1 spine is frozen and not re-litigated: Node 24 LTS · NestJS 12.1.2 · TypeScript 6.0.3 (exact pin) · Express (not Fastify) · native `mongodb` driver (not Mongoose) · Redis ≥8.2 with ioredis 6 · BullMQ 6.3.11 · `jose` (not `@nestjs/jwt`) · `@formio/js` 5.6.1 · `@casl/ability` · KMS-backed AES-256-GCM secrets · manual OpenTelemetry with OTLP → Tempo/Jaeger · `openid-client` for OIDC. **v2 adds exactly three runtime dependencies and one types-only package.** Everything else — webhook HMAC, group storage, group RBAC, credential sealing, retry, scheduling — reuses what already ships.

**Core additions:**

- **`ai@7.0.148`** — the AI guard's engine, used *only* as the implementation behind a `JevProvider`. Provider-agnostic, Zod-native, `Output.object()` for schema-constrained output, `stopWhen: isStepCount(n)` for bounded multi-turn. `generateObject` was removed in AI SDK v6 — do not import it.
- **One `@ai-sdk/*` provider package** (e.g. `@ai-sdk/openai` or `@ai-sdk/anthropic`) — chosen per deployment through the existing JEV registry. **Never** add `openai` or `@anthropic-ai/sdk` as a direct dependency: that re-creates the vendor lock-in the seam exists to prevent, and `@anthropic-ai/sdk@1.0.0` shipped on 2026-10-21 — a one-day-old `1.0.0` is not a pin.
- **`node-telegram-bot-api@2.1.0`** — Telegram adapter. Zero runtime dependencies, ESM-only (repo is already ESM), uses Node's global `fetch` so it rides the OTel-instrumented `undici` path. `grammy` is rejected despite ~20× the downloads because it pins `node-fetch@^2.7.0`, the one HTTP path OTel does not instrument — the v1 reason, re-verified and now stronger.
- **`@microsoft/microsoft-graph-types@2.43.1`** — types only, zero runtime deps. Graph calls go over `undici` to keep one instrumented HTTP path; `@microsoft/microsoft-graph-client@3.0.7` is optional and discouraged (last real publish 2023-09-19, needs its fetch path verified).

**Deliberately not added:** `zca-js` (ToS-violating, ban risk) · `@zaloapi/oa` / `zalo-oa` / `node-zalo-bot` (stale, unlicensed, deprecated) · `langchain` / `@langchain/core` (pulls `langsmith` third-party telemetry — a data-residency and NFR-O conflict) · `@modelcontextprotocol/sdk` (makes tools *reachable*, the inverse of permission-first) · every npm SCIM package (they all implement the **inbound server** half; v2 needs an outbound read) · `axios` on any new path · `@nestjs/schedule` for anything durable · `@azure/msal-node` (depends on `jsonwebtoken`, rejected in v1) · `cockatiel`/`opossum`/`p-retry` (BullMQ backoff is already the single retry mechanism) · `@slack/scim-sdk` (404 — does not exist).

**Scheduled, not in this milestone:** OpenTelemetry JS shipped **3.0.0 / 0.300.0 on 2026-10-20** — a major breaking release (removed `sdk-trace-node`, `sdk-trace-base`, `exporter-jaeger`; deep imports now fail with `ERR_PACKAGE_PATH_NOT_EXPORTED`; `spanProcessor`→`spanProcessors`). The repo already uses the new option names, so the migration is small, but it is a whole-tree change. **Do not bump during v2 feature work**; schedule it as one isolated change with the STACK.md §10.1 checklist.

### Expected Features

**Must have (table stakes — without these, v2 does not read as "the same product on more platforms"):**

- **Telegram adapter** — webhook receiver with `secret_token` verification, slash commands, inline keyboards, thread-aware replies, normalised to the existing `InboundEvent`/`OutboundMessage`. Proves the shared multi-platform seam on the lowest-risk platform.
- **Zalo OA adapter** — signature-verified receiver, 2-second ack, retry-tolerant ingest, OA access-token lifecycle with single-flight rotation, quota-aware consultation-message send, correct message class per recipient. The milestone's headline capability and its highest-risk item.
- **Two-way inbound webhooks** — signed endpoint, external-entity → `submission_id` mapping, notification delivered back to the original submitter, per-platform thread semantics, idempotent on redelivery.
- **Group-based RBAC** — group→role binding per app, platform membership reads, join/leave handling, bounded staleness, and a *real* RBAC resolver underneath.
- **Permission-first AI guard** — the model selects from the pre-filtered tool set and never invokes; bounded clarification with re-authorisation at display time; disambiguation between high-confidence alternatives; multi-turn context.
- **The three contract amendments** — `thread_id?` + `reply_to_message_id?` on both envelopes, `native_event_id?` on the inbound envelope, and a platform-scoped conversation-reference model.

**Should have (competitive — the differentiators):**

- **One normalised contract across four platforms with genuinely different delivery semantics.** Slack has threads and buttons; Telegram has inline keyboards; Zalo has *neither* — it has a 7-day consultation window, a per-user quota, and quote-replies. Doing the translation honestly, including degrading gracefully where a platform cannot thread, is the differentiator. Most gateway products pick one platform's semantics and bolt the rest on.
- **Permission-first AI guard — the model chooses, it never invokes.** No competitor gates the *tool set* by the requesting user's role.
- **Two-way sync that lands in the right thread, addressed to the right submitter.** The failure mode of naive two-way sync is an orphan top-level message sent to a different person.
- **Group RBAC with revocation that actually revokes.** The tempting version maps group→role and stops. The real version handles stale membership, group-scoped precedence, and audit attribution that does not blame the user for a sync job's grant.
- **A Zalo adapter built to Zalo's actual rules** rather than a Slack-shaped clone — quota read *before* send, 7-day window, `num_retry` redelivery.
- **Graceful degradation on Telegram privacy mode** — cheapest differentiator in the set, and it prevents a whole category of "it's broken" tickets.

**Defer (v2.x / v3):**

- Notification topic subscriptions (FR-N-5), per-app notification muting (FR-N-7) — trigger: user demand after two-way sync lands.
- Zalo GMF group targeting — trigger: a customer actually asks; requires the group-management permission grant.
- Telegram forum-topic-aware threads, privacy-mode diagnosis surfaced in-product (P2 in the matrix).
- **Directory sync via SCIM / Entra ID as the authoritative upstream** — largest cost in the group-RBAC area, least differentiating, and every npm SCIM package is the inbound-server half. v3.
- Native IM form rendering (Block Kit / Zalo Mini App forms) — contradicted by NG3 and AD-3. One engine, one renderer. **P4, out of scope.**
- Cross-app collection sharing, multi-step approval workflows, the remaining 29 IM platforms — v3+.
- **Anti-features to keep out of the roadmap:** open-ended free-form chat · model tool-calling / function-calling APIs · auto-executing a form submission from the guard · broadcasting notifications to an entire IM group · long-polling as a Telegram fallback (mutually exclusive with webhook) · a second `InboundEvent` schema variant per platform · a Zalo Mini App as a second form surface.

### Architecture Approach

The v1 topology is unchanged — three NestJS entrypoints, one DI graph, one boundary-enforced element graph, BullMQ queues. What changes is **where the new work attaches**. The core architectural move is that a platform becomes **a pair of plug-ins**: an inbound normaliser in `apps/api/src/adapters/<platform>/` and an outbound delivery port in `packages/domain/src/adapters/<platform>/outbound/`, registered once in an `AdapterRegistry` that asserts at boot that every `ImPlatform` value has exactly one inbound descriptor and one outbound port (a half-registered platform is a startup failure, not a runtime 500). Between them sits a new **outbound delivery seam** — an `im-outbound` queue, an `OutboundMessageProcessor` with jittered backoff and DLQ, and an app-layer `OutboundDispatcher` that resolves `platform → PlatformDeliveryPort`. The seam's placement is forced by the boundary graph: the `outbound-adapter` file category already exists in `tooling/boundaries.config.mjs` and is restricted to `apps/worker`, but it currently matches nothing because the Teams delivery service was placed in an app directory — moving it into the domain category makes R1 finally enforce "only the worker may send." Because `adapters` may import only `platform, kernel, contract`, the delivery port takes the conversation reference **as a parameter** and the app-layer dispatcher resolves it. Underneath, the **platform-event ledger** (a MongoDB collection per platform, unique index on the platform's own event id, `pending → dispatched` state plus a scheduler-driven reconciler) is the durable idempotency guarantee — not Redis `SETNX`, not BullMQ `jobId`. Group RBAC uses a **stored, monotonic per-`(user, app)` epoch** bumped in bulk with `updateMany`; the epoch is embedded in the Redis cache key, so revocation is one write and zero cache deletes, and D-21's claim set is untouched. The AI guard is a **`GuardedProvider` decorator** implementing `JevProvider`: it inspects the request, calls the inner provider, and re-validates the chosen tool against the permitted set on the way out. The decision layer asks "what may this user use"; the guard asks "may this conversation proceed." It never decides what to say.

**Major components (new or materially modified in v2):**

1. **Outbound delivery seam** (`im-outbound` queue, `OutboundMessageProcessor`, `OutboundDispatcher`, `PlatformDeliveryPort`, `AdapterRegistry`) — the missing half of v1; makes every adapter two-sided by construction.
2. **Event-envelope amendments** (`InboundEvent`/`OutboundMessage` gain `thread_id?`, `reply_to_message_id?`; `InboundEvent` gains `native_event_id?`) — optional, backward-compatible, no spec-version bump; the `events.spec.ts` strictness test is the mechanical guard.
3. **Platform-scoped conversation reference** (key `${platform}::${scope_kind}::${scope_id}::${chat_user_id}`, validated per-platform discriminated-union payload instead of `unknown`) — plus a migration of the v1 Teams-shaped rows.
4. **Real RBAC and persistent identity** (`RbacService` evaluates direct ∪ group-derived assignments; `perm_version` becomes a required parameter with no `= 0` default; RBAC cache moves from an in-process `Map` to Redis with the epoch in the key; identity mapping becomes Mongo-backed with a Redis read-through cache; the inline `authorize` closure in `apps/worker/src/app.module.ts` is replaced).
5. **Platform-event ledger** (generalised `PlatformEventRepository`, one collection per platform, unique index on the platform event id, `pending → dispatched` plus reconciler, 30-day retention sweep).
6. **Group element** (`packages/domain/src/groups/` — memberships, group→app role assignments, `GroupSyncService`, `GroupBindingService`, a pluggable `DirectorySource` port; a **new element type** in `boundaries.config.mjs`).
7. **Credential repository** (`SecretEnvelope`-backed store for the Zalo OA secret and Telegram bot token — R2's owners only; no `process.env` secret in any adapter).
8. **`GuardedProvider` + `PromptGuardService`** (the AI guard, as a provider decorator; no new pipeline stage).

### Critical Pitfalls

1. **Zalo's webhook signature is a plain hash used as a MAC, over a body that must stay byte-identical.** The documented algorithm is `sha256(app_id ‖ rawBody ‖ timeStamp ‖ OAsecretKey)` — **not HMAC** (several community guides misstate it), over the **raw bytes** (NestJS's `@Body()` gives a parsed object; re-serialising changes the bytes), using the **OA** Secret Key (**not** the App Secret Key). Three failures, one indistinguishable symptom: every event rejected with 401. *Avoid:* one implementation module (`ZaloWebhookVerifier` under the `inbound-adapter` category), raw-body capture via `rawBody: true` / `@RawBody()`, `crypto.timingSafeEqual` on equal-length buffers with a shape check first, and a **frozen captured-request test vector** — a synthesised body is byte-perfect by construction and will not catch this.
2. **The receiver has a message-loss window, and Zalo's 2-second budget ends in *silent* webhook death.** The current order is insert-dedupe-row → upsert-conversation-ref → `queue.add`; a crash between the insert and the enqueue leaves the row saying "seen" and the event never queued — and because the platform got a 2xx, it will not retry. Zalo retries 5× (30 s / 5 m / 15 m / 30 m / 1 h) and then **disables the webhook with no email, no API, no warning**; re-enrolment is a manual portal action. *Avoid:* close the window with a `pending → dispatched` state plus a scheduler reconciler; make the receiver a pure ingest contract (verify → validate → enqueue → 200, no DB read, no KMS decrypt, no outbound call); alert at ack **p99 > 1.2 s**, not at the 2 s cliff; add a **per-OA event-freshness probe** — a liveness check stays green through a disabled webhook.
3. **v1 shipped an authoriser that grants everything.** `RbacService.hasPermission` returns `true` unconditionally; `getRoles` returns `['employee']`; `perm_version` defaults to `0`; the RBAC cache is an in-process `Map`; the identity mapping is an in-memory array; the worker's real authorisation is an inline closure reading `def.role_assignments` as `Record<string, unknown>`. Every pod has its own cache, so a revocation on pod A does not evict pod B — and a worker restart forgets every identity mapping. *Avoid:* treat this as a **v1 correctness fix inside Phase 11**, not a v2 feature. Make `perm_version` a **required** parameter (the compile error is the point), move the cache to Redis with the epoch in the key, persist identity in Mongo, and delete the duplicate inline authoriser.
4. **The AI guard that can *act*.** The failure mode is not "the model picks the wrong tool" — it is "the model calls something it was never granted", or is prompt-injected through user text, form values, connector responses, or documents, or loops, or exfiltrates via a connector tool. Two subtler traps: **LLM confidence is a soft, uncalibrated self-report** — using it as a *permission* signal is a category error (it is a *ranking* signal); and **the fallback chain is itself a permission surface** — a fallback that guesses the most likely tool is a bypass. *Avoid:* the model *proposes*, the platform-side gate *disposes*; compute the permitted set **before** the call and only intersect afterwards; re-check permission **at execution** with the current epoch; every fallback returns `clarify` on uncertainty; cap the tool catalogue and *narrow* by relevance rather than truncate; treat model-visible content as untrusted.
5. **Frozen contracts do not get edited — they get worked around.** D-21 (read-link claims) and D-23 (JEV v1 wire) are exactly where v2 wants to change something, and a careless edit invalidates every outstanding link or every provider built against `1.0`. *Avoid:* express the shorter notification TTL in the **issuer** (the 90-day ceiling is a maximum, already enforced by `.refine()`); resolve the notification destination from `real_user_id` → conversation reference at send time instead of adding a `target_id` claim; keep the guard's contract footprint at zero by making it a provider decorator; enforce a tool-count cap as a **precondition**, not a schema change. For D-16/D-18, **widen the allowlist deliberately** (`app_id`, `perm_version`, `group_id`; opaque ids, never names) with the written justification in the same commit — never smuggle an identifier through `reason`.

**Additional high-value pitfalls flagged by research** (each maps to a phase below): Zalo's 19-digit ids exceed `Number.MAX_SAFE_INTEGER` and `JSON.parse` rounds them silently, merging two users into one identity (ids must be strings end-to-end; fixtures must use the real values) · Zalo's 25 h / 90-day **single-use rotating** refresh token needs single-flight under a Redis lock, KMS-encrypted, with a one-click re-authorisation flow · Zalo's **Vietnam-egress rule** silently empties user profile data and collides with the region-locked residency constraint · Telegram's `callback_data` **64-byte** cap (exceeding it fails the entire message) and mandatory `answerCallbackQuery` · Telegram commands carry **no scope** and privacy mode hides most group traffic · Telegram's `allowed_updates` must be set explicitly and asserted at boot, and `update_id` is **randomised** after a week of inactivity · Slack can deliver the same message with **different `event_id`s**, so dedupe needs a second key on the message `ts` · Graph's `syncStateNotFound` and `410 + empty $deltatoken` are **terminal**, not retryable · the `groups` element and every new adapter directory must be declared in `boundaries.config.mjs` or the build fails with an unhelpful default-deny message.

### Cross-Cutting Non-Negotiables

1. **The outbound seam comes before any adapter.** Shipping a Zalo adapter first produces a bot that receives perfectly and never answers.
2. **Real RBAC comes before group RBAC and before the AI guard.** "Permission-first" over a stub authoriser is a claim, not a guarantee.
3. **The AI guard is a `JevProvider` decorator, never a pipeline stage.** It never sees an unfiltered tool set; it refuses bad text and bad output, and re-validates the chosen tool on the way out.
4. **D-21 and D-23 are not edited.** Group revocation folds into the existing `perm_version` integer; the guard inherits the frozen JEV wire contract unchanged.
5. **The receiver is a pure ingest contract.** Verify → validate shape → dedupe → enqueue → 200. Everything else is in the consumer. This holds for all four platforms and is now a 2-second budget on Zalo.

## Implications for Roadmap

Based on the combined research, the suggested v2 phase structure is **eight phases, 10 through 17**, continuing v1's numbering.

### Phase 10: Outbound Delivery Seam & Event Contract
**Rationale:** The single highest-leverage phase in the milestone. Everything downstream assumes it, and it is independently demonstrable: **the bot finally answers.** ARCHITECTURE finding #2 and #3 and PITFALLS 9/10/15 all point here. The envelope amendment (`thread_id?`, `reply_to_message_id?`, `native_event_id?`) must land here because every later phase inherits it and retrofitting it invalidates already-shipped adapters.
**Delivers:** `im-outbound` queue constant + `OutboundMessageProcessor` (jittered backoff, DLQ) + app-layer `OutboundDispatcher`; `PlatformDeliveryPort` + `AdapterRegistry` with a boot-time assertion that every `ImPlatform` has exactly one inbound and one outbound; `InboundEventProcessor` enqueues its own `OutboundMessage` instead of returning it; Teams + Slack delivery ports moved into `packages/domain/src/adapters/<platform>/outbound/` and the uncalled `apps/api/.../teams.outbound.service.ts` deleted; the `OutboundMessage.message_id` generated by the producer and stable across retries; platform-scoped conversation-reference model with a validated per-platform payload (replacing `unknown`) plus a migration of v1 rows; envelope amendments with the `events.spec.ts` strictness test updated; the Slack receiver placeholder (`return {ok:true}`) replaced by a real receiver (raw body → `v0:` HMAC → envelope → enqueue) — the highest-value defect in the repo; `PlatformEventRepository` generalised from the Teams shape, one collection per platform, unique index on the platform event id, `pending → dispatched` state plus a `platform-event-dispatch` reconciler; boundary-graph extension (`outbound-adapter` category now matches something; `groups` element declared ahead of use).
**Addresses:** FEATURES P1 enablers — `OutboundMessage` thread/reply contract extension; per-platform ordering + dedupe layer; the Slack receiver defect; PITFALLS P9, P10, P15.
**Avoids:** PITFALLS 1 (no outbound work in a receiver), 9 (dedupe by unique index, not Redis/`jobId`), 10 (platform-scoped, validated conversation reference), 15 (adapter placement under `{inbound,outbound}` so R1 applies).
**Uses:** BullMQ 6.3.11 · `mongodb` native driver · `node:crypto` `timingSafeEqual` · existing `rawBody: true` plumbing.
**Research flag:** **no** deep research needed — the patterns are in-repo. Planning task instead: a short written decision memo on the four contract questions (envelope field names, `native_event_id` semantics, `platform_metadata` shape, notification-link TTL policy) so the amendment lands once.

### Phase 11: Real Authorization & Persistent Identity
**Rationale:** A **v1 correctness fix** that gates two later phases. ARCHITECTURE finding #4 and PITFALLS 11 both say the same thing: group RBAC is impossible on top of a stub, and the AI guard's central claim is meaningless until it holds. Doing this before the adapters means every adapter lands on real authorization.
**Delivers:** `RbacService` evaluates real effective permissions for `(app, user)` from direct assignments ∪ (later) group-derived assignments; the inline `authorize` closure in `apps/worker/src/app.module.ts` deleted; `perm_version` becomes a **required** parameter (the `= 0` default removed) and sourced from a real `user_app_epochs` store; RBAC cache moves from an in-process `Map` to Redis with the epoch in the key (`ak:rbac:{app}:{user}:{perm_version}`); identity mapping and profile repositories become Mongo-backed with a Redis read-through cache and immediate invalidation; `SecretEnvelope`-backed `PlatformCredentialRepository` for per-tenant IM secrets (no `process.env` secret in any adapter); D-16/D-18 allowlist widened **with written justifications in the same commit** (`app_id`, `perm_version`, `group_id` — opaque ids only; `event_id`, `channel_id`, `thread_id`, `reply_to_message_id` stay out); boundary edges for the new element.

### Phase Ordering Rationale

- **Phase 10 is the gate for everything.** It carries the outbound seam (without which no adapter is demonstrable), the envelope amendments (without which FR-IM-8 threading and correct dedupe are inexpressible), the platform-scoped conversation reference (without which the second platform can collide with the first), the boundary-graph extension (without which the lint build fails with an unhelpful message), and the Slack receiver fix (every later Slack verification depends on it). Changing any of these after an adapter ships invalidates the adapter.
- **Phase 11 is the gate for the two security-bearing phases.** Group RBAC binds to roles; the AI guard's candidate set is the authorized set. Both are theatre over a stub authoriser. The fix also closes a v1 defect rather than adding a v2 feature — it is the honest place to spend the milestone's foundation budget.
- **Foundations before adapters; adapters before sync; sync before groups; groups before the guard.** The dependency chain is not a preference: the guard's permitted set is the union of app-scoped and group-scoped permissions, so building it before the group axis exists means building it against a stub. The two-way sync is what makes group-scoped notifications possible and is where the conversation-reference model is exercised.
- **Telegram before Zalo, but Zalo's clock starts immediately.** Zalo's critical path is human — OA approval, permission grants, VN egress — so those requests go out during Phase 12. The *build* order follows the risk order: prove the seam on the platform with no unknowns, then build the platform with every unknown.
- **Phases 13 (Zalo) and 14 (two-way sync) can run in parallel** once Phase 10 lands; they touch different adapters and different queues. Phase 15 (groups) can also run alongside Phase 13's directory-sourced half, which needs no Zalo. A two-engineer team can compress 12–15; a one-engineer team should follow the sequence.
- **The order minimises every pitfall's blast radius.** Doing the contract work first (P14), the real epoch before the group axis (P11), the ledger before the dedupe machinery (P9), and the outbound seam before any adapter (Anti-Pattern 1) is what converts "silent failure" pitfalls into "loud failure" ones.
