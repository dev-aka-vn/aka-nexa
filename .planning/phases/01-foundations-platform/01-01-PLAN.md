<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public registry → build | Package resolution is untrusted supply-chain input; an unpinned install can resolve a breaking TypeScript. |
| CI runner → repository | The install-guard job intentionally deletes a tracked file; a weakened guard silently re-opens the TS 7.x install. |
| HTTP client → api | The `/health/live` route is the first untrusted-input surface; it must read no dependency. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-01 | Tampering | `package.json` / `package-lock.json` | high | mitigate | Exact `typescript: "6.0.3"` pin + committed lockfile + CI job that asserts the resolved pin (FND-01/FND-02). |
| T-1-02 | Tampering | `.github/workflows/ci.yml` install-guard job | high | mitigate | The guard deletes the lockfile and runs a lockfile-free `npm install`; a Node assertion in the plan fails if `--force`/`--legacy-peer-deps` is present (D-06). |
| T-1-03 | Denial of Service | `apps/api` `/health/live` handler | medium | mitigate | Liveness reads no dependency, so a downed Mongo/Redis cannot cascade into a restart loop (FND-05 liveness half). |
| T-1-SC | Tampering | npm installs | high | mitigate | Every package is carried in `STACK.md §14`; any package added here that is not in that ledger requires a `checkpoint:human-verify` against `npmjs.com/package` before install. |
</threat_model>
