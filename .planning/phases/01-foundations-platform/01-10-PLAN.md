## Phase Goal

> Same derivation as plan 01: the ROADMAP goal is not in user-story format, so it is restated, not invented. **As a** platform operator, **I want to** run three independently bootable processes that each expose health, readiness, and metrics and cannot drift into one another, **so that** the operational contract is fixed before any user-facing feature lands.

<objective>
Finalise the three entrypoints. Give each app an `otel.mjs` loader entry and a `main.ts` that starts
OTel first, dynamically imports `app.module.js`, boots via `NestFactory.create()`, and calls
`enableShutdownHooks()`. Compose each `app.module.ts` from the platform surface, mount the shared
health, readiness, and metrics surfaces on all three, give the worker the one `platform-heartbeat`
BullMQ `Worker`, give the scheduler the `platform-heartbeat` Job Scheduler, wire the per-app
`BoundaryManifest` into the shared `ProviderBoundaryGuard`, compose the platform barrel, remove the
tracer's app-local health controller, and add the import-closure drift test.

Purpose: FND-03 is the "three entrypoints never drift" requirement; this is the plan that installs the
independent bootstrap, the per-app manifests, and the negative test that keeps the three from
converging. D-09's `enableShutdownHooks()` is what makes a rolling deploy drain in-flight work instead
of killing a submission mid-transaction.

Output: three independently bootable ESM processes with health, readiness, metrics, OTel, and the
boundary guard wired, plus the drift test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| entrypoint → DI container | A provider from a forbidden module could be instantiated dynamically and evade static lint. |
| process → operating system | SIGTERM during a rolling deploy must drain in-flight work, not abort it. |
| app source → app bundle | A shared bundle or a cross-app import collapses the three-process model. |
