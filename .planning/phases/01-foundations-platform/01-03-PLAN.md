## Phase Goal

> Same derivation as plan 01: the ROADMAP goal is not in user-story format, so it is restated, not invented. **As a** platform engineer, **I want to** have the component boundary model enforced by a build-failing lint rule and a boot-time runtime assertion, **so that** a cross-boundary import or a dynamically-resolved forbidden provider cannot ship unnoticed.

|------|---------------|------|

| const | `boundariesDependenciesRule` | `default: "disallow"` + R1/R2/R3 policies |
| config | `eslint.config.mjs` | flat config; boundaries + `no-restricted-imports` |

<objective>
Make the component boundary model a build failure, not a convention. Add the `eslint-plugin-boundaries` v7
settings and dependency rule — element types for kernel/platform/contract/thirteen domain subdirectories
and three distinct app types, file categories for the adapter/http/worker/scheduler/secrets/data-access
surfaces, and R1/R2/R3 policies. Add the ESLint-core `no-restricted-imports` rule that a boundaries module
selector cannot express (the BullMQ `Worker` named binding). Then add the runtime `ProviderBoundaryGuard`
that aborts boot when a forbidden token has actually been resolved in the Nest container.

Purpose: FND-04 is the phase's headline constraint. `ARCHITECTURE.md` describes a v5 config shape; the
installed plugin is v7 where `boundaries/files` is a settings block, not a rule. Getting this wrong means
silent under-enforcement, so this plan ships a per-category violation smoke test rather than trusting the
config by inspection.

Output: a build-failing boundary rule, a separate named-binding restriction, and a runtime boot assertion
behind one Nest-internals seam.
</objective>
