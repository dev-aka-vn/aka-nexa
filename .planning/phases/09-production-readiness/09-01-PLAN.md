<objective>
Make the audit trail durable and policy-governed: move it off the per-process in-memory array onto a Mongo `audit_entries` collection (D-01), give the retention service a single named delete ownership enforced by a guard test (D-04), run a scheduled retention sweep that deletes only rows strictly older than a three-year cutoff and appends its own summary entry (D-03), implement a two-phase app purge (soft-delete then hard-delete after a grace period) with a terminal `purged` lifecycle state and a grace-period record (D-13), and mark archived vs purged scope membership in the App Builder console.

Purpose: This is the write-side half of the compliance story (ROADMAP success criteria 1 and 2). Without a durable store, "3-year retention" is a statement about an array that dies with the process; without a retention sweep the trail grows unbounded; without a two-phase purge there is no auditable way to actually remove data; without a single named delete owner, AUD-01's append-only guarantee degrades from "no methods exist" to "somebody might add one"; without the console marking an operator cannot tell why a submission's app is absent.
Output: A Mongo-backed `AuditRepository`, a closed audit-entry type module, two new sweep registrations and consumers (retention + purge), two domain services, a single-owner guard test, an amended lifecycle contract, a new config key, and the console scope-picker marking.

Scope decision (D-01/D-02/D-06/D-08/D-14/D-21): the retention sweep and the purge sweep are **separate named single owners** — separate services, separate registrations, separate processors, separate guard tests. RESEARCH Q1 resolved: do not collapse them into one "cleanup job"; the erasure path (plan 09-02) is a third, also separate, owner. Three owners, three guard tests.

D-04 sharpens AUD-01: the repository stops *proving* append-only by omitting methods and instead grants **one greppable exception** — the retention service — and a guard test that fails if any other module deletes audit rows. The `deleteOlderThan` method added here is that exception and is the only delete path on the collection.

WINDOW 7 (D-21) is **not** in this plan — key rotation is plan 09-06. This plan deliberately does not touch `packages/platform/src/crypto/envelope.ts`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process -> Mongo `audit_entries` | The trailing store crosses a process boundary; the api and the CLI must see each other's entries, which the in-memory array could not do. |
| retention service -> audit collection | One module holds a delete capability over an append-only trail; every other module must not. |
| scheduler -> worker queue | A scheduled trigger crosses into the worker process; the payload must not be trusted to name the cutoff or the grace window (both come from config inside the consumer). |
| operator -> purge command | An authenticated admin triggers an irreversible data deletion; the operator identity is the only attribution the audit record will have. |
| config -> retention/purge windows | A mis-set window either deletes compliant data early or never deletes at all. |
| App Builder client -> apps listing API | Scope-picker membership is rendered from server data; a client that infers membership can show a purged app as live. |

ASVS level 1 (`security_asvs_level: 1`, `security_block_on: high`): mitigate critical/high on primary boundaries; accept lower-severity with a named rationale.
