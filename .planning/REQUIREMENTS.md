# Requirements: aka-nexa — Milestone v2.0

**Defined:** 2026-10-22
**Milestone:** v2.0 — Platform Expansion & Advanced Capabilities
**Core Value:** An employee can complete a cross-system task entirely through chat plus a single rendered form, without ever logging into — or learning — the downstream system.

**Previous milestone:** v1.0 (shipped 2026-10-21, 9 phases / 72 plans) — see `.planning/milestones/v1.0-REQUIREMENTS.md`.

**Research basis:** `.planning/research/SUMMARY.md` (4 parallel passes: STACK, FEATURES, ARCHITECTURE, PITFALLS).

---

## Scope Framing

v2 **completes** the v1 chat loop rather than extending it. The v1 research found two structural gaps that make
every v2 capability meaningless until they are closed:

1. **The outbound half of the product does not exist.** `InboundEventProcessor.process()` returns a link that
   BullMQ discards; `TeamsOutboundService` has no caller; the only live outbound path hardcodes
   `TeamsDeliveryService`. The Slack receiver is a placeholder (`return {ok:true}`).
2. **v1 shipped an authoriser that grants everything.** `RbacService.hasPermission` returns `true`
   unconditionally; `getRoles` returns `['employee']`; `perm_version` defaults to `0`; the RBAC cache is an
   in-process `Map`; identity repositories are in-memory.

Both are **foundations-first** work: OUT (Phase 10) and AUT (Phase 11) gate the six capability categories.

### PRD Amendment

**NG1 (open-ended conversational AI) is amended, not reversed.** The model gains a wider *input* space
(free-text intent); its *action* space stays narrower (select a pre-authorised app). It may never invoke a
tool, never emit free-form generated content, and never see an unauthorised app. The v1 invariant that the
model never sees an unauthorised tool is preserved **structurally** (platform pre-filters → model selects →
platform executes), not by prompt.

## v2.0 Requirements

### OUT — Outbound Delivery Seam & Event Contract (Phase 10)

The delivery seam that makes every adapter demonstrable. Without it, an adapter receives perfectly and
never answers.

- [ ] **OUT-01**: A message produced by the inbound pipeline is delivered back to the originating IM conversation, not discarded.
- [ ] **OUT-02**: Outbound delivery is executed asynchronously by a queue worker with jittered exponential backoff and a dead-letter queue, so a platform outage never blocks the inbound path.
- [ ] **OUT-03**: Every IM platform has exactly one inbound adapter and exactly one outbound delivery port, asserted at boot — a missing or duplicate registration fails startup rather than failing silently at runtime.
- [ ] **OUT-04**: The Slack inbound receiver verifies the `v0:` HMAC-SHA256 signature over the raw request body before accepting an event; the placeholder receiver that returned `{ok:true}` is removed.
- [ ] **OUT-05**: An inbound event carries an optional `thread_id`, an optional `reply_to_message_id`, and an optional `native_event_id`, so a reply can be routed to the thread it answers.
- [ ] **OUT-06**: The inbound envelope accepts an optional `platform_metadata` record carrying non-PII platform-specific fields; platform-specific payload never leaks past the adapter boundary.
- [ ] **OUT-07**: A conversation reference records the platform, the platform-scoped conversation identifier, and a validated per-platform payload; a second platform can never collide with the first.
- [ ] **OUT-08**: The outbound message identifier is generated by the producer and remains stable across every delivery retry.
- [ ] **OUT-09**: A platform event is recorded in a platform-scoped ledger with a unique index on the platform event identifier and moves through `pending → dispatched`; a crashed delivery is reconciled by a scheduled job rather than lost.
- [ ] **OUT-10**: The inbound receiver verifies the signature, validates the envelope shape, deduplicates, enqueues, and returns — it performs no database read, no credential decryption, and no outbound call.
- [ ] **OUT-11**: The platform event ledger is swept of entries older than 30 days.
- [ ] **OUT-12**: The outbound delivery implementation for each platform lives under that platform's adapter directory, so the architecture boundary rule applies to outbound code as well as inbound.
- [ ] **OUT-13**: The trace context of an inbound event is propagated into the outbound delivery attempt, so a reply is traceable to the message that caused it.
- [ ] **OUT-14**: A dead-lettered outbound message is visible on an operator surface with its failure reason and the platform event that produced it.

### AUT — Real Authorization & Persistent Identity (Phase 11)

A v1 correctness fix, not a v2 feature. Group RBAC and the AI guard are theatre over a stub authoriser.

- [ ] **AUT-01**: The effective permissions of a user for an app are resolved from the union of directly-assigned and group-derived role assignments; an unassigned user has no permission.
- [ ] **AUT-02**: A permission check with no explicit permission version is a compile error, not a silent default.
- [ ] **AUT-03**: The permission version is read from a persistent per-user-per-app epoch store; a revoked assignment increments it.
- [ ] **AUT-04**: The authorisation decision cache lives in Redis, keyed by app, user, and permission version, so every replica agrees on a revocation.
- [ ] **AUT-05**: Resolved identity mappings and profiles persist in MongoDB and are read through a Redis cache invalidated on change.
- [ ] **AUT-06**: Exactly one authorisation implementation exists in the codebase; the inline closure that duplicated the role check is removed.
- [ ] **AUT-07**: A user's platform credentials are stored in a KMS-backed secret envelope; no adapter reads a secret from a plaintext environment variable.
- [ ] **AUT-08**: The audit field allowlist is widened to carry the app identifier, the permission version, and the group identifier as opaque values, with the justification recorded in the same change.
- [ ] **AUT-09**: A permission denial produces a clear, user-facing message naming what was denied, not a generic error.
- [ ] **AUT-10**: A permission check is performed at both points required by the v1 design — before the decision model sees the tool set, and again immediately before execution.

### TGA — Telegram Adapter (Phase 12)

The lowest-risk platform. It proves the shared seam from Phase 10.

- [ ] **TGA-01**: A Telegram webhook endpoint receives updates and rejects any update whose `secret_token` header does not match the configured secret, compared in constant time.
- [ ] **TGA-02**: A Telegram message is normalised into the shared inbound envelope with the platform event identifier derived from the update and message identifiers.
- [ ] **TGA-03**: A Telegram message is answered in the thread it arrived in, using the platform's reply and topic parameters.
- [ ] **TGA-04**: A Telegram slash command is rejected unless the sender is authorised for the target app — command registration is a user convenience, never the authorisation boundary.
- [ ] **TGA-05**: A Telegram inline keyboard choice encodes an opaque server-side handle; the encoded payload never exceeds 64 bytes and the message fails to send if it would.
- [ ] **TGA-06**: A Telegram callback query is answered with `answerCallbackQuery` before any other work, so the user's button never spins.
- [ ] **TGA-07**: The set of subscribed update types is declared explicitly at boot and verified against the platform's live webhook configuration; a mismatch fails startup.
- [ ] **TGA-08**: When the bot cannot observe group messages, the user receives a diagnosis naming the exact administrative step required, rather than silence.
- [ ] **TGA-09**: Telegram delivery respects both the platform's per-chat rate limits and the platform's own per-user and per-app limits.
- [ ] **TGA-10**: A Telegram update identifier is used only as a deduplication key, never as an ordering cursor.
- [ ] **TGA-11**: A Telegram reply can be edited in place to replace an expiring link, rather than being re-sent as a second message.

### ZAL — Zalo OA Adapter (Phase 13)

The milestone's headline capability and its highest-risk item.

- [ ] **ZAL-01**: A Zalo webhook endpoint verifies the `X-ZEvent-Signature` digest computed over the exact raw request bytes, using the OA Secret Key, compared in constant time; an invalid signature is rejected before any other work.
- [ ] **ZAL-02**: The Zalo signature algorithm is implemented in exactly one module, and a captured real request is frozen as a regression test vector.
- [ ] **ZAL-03**: The Zalo receiver acknowledges within the platform's 2-second deadline and performs no work beyond verification, validation, deduplication, and enqueue.
- [ ] **ZAL-04**: A Zalo event redelivered by the platform's retry ladder produces exactly one processing result, deduplicated on the platform's own message identifier.
- [ ] **ZAL-05**: The OA access token is refreshed ahead of expiry by a scheduled job, the refresh is single-flighted under a lock so concurrent workers cannot race, and the rotating refresh token is stored KMS-encrypted.
- [ ] **ZAL-06**: A failure to refresh the OA token is surfaced to an administrator as an expiry countdown with a one-click re-authorisation path, not as a silent adapter failure.
- [ ] **ZAL-07**: A Zalo identifier is carried as a string end-to-end; two distinct users with 19-digit identifiers never collapse into one identity.
- [ ] **ZAL-08**: A deployment that cannot egress from the required region fails a typed startup check rather than silently resolving users as unknown.
- [ ] **ZAL-09**: Before a consultation message is sent, the remaining quota for that user is read from the platform's quota API; an exhausted quota is a distinct, visible outcome rather than a generic send failure.
- [ ] **ZAL-10**: A user outside the platform's consultation window receives a distinct visible outcome rather than a generic send failure.
- [ ] **ZAL-11**: The three Zalo message classes — consultation, group, and broadcast — are sent through their correct class for the recipient.
- [ ] **ZAL-12**: A non-text Zalo event (image, link, audio, video, sticker, location, business card, file) is acknowledged with a typed "unsupported" outcome and the list of supported actions; it is not silently dropped.
- [ ] **ZAL-13**: A Zalo follow and unfollow event is handled and reflected in who can be messaged.
- [ ] **ZAL-14**: The Zalo client is hand-written over the platform's HTTP API with no third-party Zalo package; no unofficial, unlicensed, or deprecated Zalo dependency is introduced.
- [ ] **ZAL-15**: Text sent to Zalo is truncated to the platform's 2000-character limit inside the client, not by silently widening the outbound contract.

### SYNC — Two-Way Synchronisation & Delivery Semantics (Phase 14)

The capability that turns the gateway into a two-way integration surface.

- [ ] **SYNC-01**: An external system can post a signed notification to the platform, and the signature is verified against the connector's secret over the raw body before the payload is parsed.
- [ ] **SYNC-02**: A replayed external webhook — same signature, same timestamp, same nonce — is rejected.
- [ ] **SYNC-03**: An external entity identifier is mapped to the submission it refers to, and an unmappable identifier produces a recorded rejection rather than a silent no-op.
- [ ] **SYNC-04**: The notification reaches the person who submitted the request, resolved from the submitter's identity at send time — not from a stored chat identifier that may have changed.
- [ ] **SYNC-05**: The submitting user's platform, conversation, and thread identity is bound to the submission at submit time; a submission created before this change cannot be retrofitted.
- [ ] **SYNC-06**: A redelivered external webhook produces exactly one notification.
- [ ] **SYNC-07**: The notification lands in the thread of the original request on platforms that support threading, and degrades to a new message in the conversation on platforms that do not.
- [ ] **SYNC-08**: The notification deep link carries a shorter expiry than the maximum view-link lifetime, expressed by the issuer — the link claim schema itself is unchanged.
- [ ] **SYNC-09**: A failed notification delivery is retried and then dead-lettered, and the dead letter is visible with a metric and an operator surface.
- [ ] **SYNC-10**: Turns within one conversation are ordered, so a multi-turn request is not assembled from out-of-order deliveries.
- [ ] **SYNC-11**: A connector without webhook support can fall back to polling at a configurable interval of at least 60 seconds.

### GRP — Directory & Group RBAC Sync (Phase 15)

Group binding is worthless without knowing who is in the group — and the real version handles stale membership.

- [ ] **GRP-01**: An app owner binds a group to a role for their app; the binding is app-scoped and does not affect any other app.
- [ ] **GRP-02**: A user's effective permissions include the union of the permissions of every group bound to the app that the user belongs to.
- [ ] **GRP-03**: A directly-assigned user role takes precedence over a group-derived role where they conflict.
- [ ] **GRP-04**: Slack group membership is read from the usergroups API, including the member list.
- [ ] **GRP-05**: Microsoft Graph group membership is read, and a terminal directory-sync state triggers a full resync rather than an unbounded retry.
- [ ] **GRP-06**: Zalo group membership is read when the deployment holds the group-management permission; without it, the source reports as unavailable rather than as an empty group.
- [ ] **GRP-07**: Telegram group membership is not offered — the platform's Bot API cannot enumerate it — and this is documented rather than silently missing.
- [ ] **GRP-08**: Losing group membership revokes the group-derived permission across every replica, and the revocation is effective on the next permission check.
- [ ] **GRP-09**: Membership staleness is bounded and observable — event-driven invalidation plus periodic full reconciliation plus a maximum-staleness window — and the bound is documented.
- [ ] **GRP-10**: A failed membership read never replaces a known-good membership set; the source is quarantined, the last good state is retained, and an alert fires.
- [ ] **GRP-11**: A group-derived grant and revocation are audited with the sync job as the actor and the group identity attached, so a synchronised grant is not mistaken for an unauthorised self-grant.
- [ ] **GRP-12**: Directory sources are read-only; the platform never writes membership back to a directory it reads from.
- [ ] **GRP-13**: A revoked app disappears from an open clarification session, preserving the v1 re-filtering invariant under the group axis.

### AIG — Permission-First Open-Ended AI Guard (Phase 16)

The model chooses; it never invokes.

- [ ] **AIG-01**: The decision model receives only the tool set the requesting user is authorised for — never the global catalogue.
- [ ] **AIG-02**: The model selects a tool; it has no mechanism to invoke one, and no tool is exposed with an executable handler.
- [ ] **AIG-03**: The platform re-validates the selected tool against the permitted set at execution time using the current permission version.
- [ ] **AIG-04**: A request exceeding the tool-catalogue cap is rejected with a typed error rather than silently truncated; the catalogue is narrowed by relevance, never cut arbitrarily.
- [ ] **AIG-05**: The model runs at zero temperature with a bounded step count and an absolute deadline.
- [ ] **AIG-06**: When no permitted tool is offered, when the model's confidence falls below the configured threshold, when a competing permitted alternative is within the disambiguation window, or when the deadline expires, the system asks a bounded clarification instead of guessing.
- [ ] **AIG-07**: Every fallback provider in the chain is subject to the same constraints, and every fallback returns a clarification on uncertainty — a fallback that guesses the most likely tool is a bypass.
- [ ] **AIG-08**: Model-visible content — user text, form values, connector responses, documents — is treated as untrusted input and cannot instruct the platform to act.
- [ ] **AIG-09**: The guard may only produce a reply, a form link, a confirmation, an error, or a status; it may never emit free-form generated content.
- [ ] **AIG-10**: The clarification prompt is generated by the model but rendered as a bounded choice surface with at most three options, re-authorised at display time.
- [ ] **AIG-11**: The guard is a decorator on the existing decision provider; the frozen decision wire contract is unchanged and no new pipeline stage is introduced.
- [ ] **AIG-12**: A cost and latency budget with a circuit breaker that opens to clarification, never to a guess.
- [ ] **AIG-13**: The model never issues the request, and the link always goes through the one-time-link form-consent path.

### OPS — Security, Compliance & Operations (Phase 17)

Not optional cleanup — the difference between a recoverable incident and a 90-day outage.

- [ ] **OPS-01**: A readiness probe reports a registered OA that has received zero events for a configurable period; a platform-side webhook disable is otherwise invisible.
- [ ] **OPS-02**: The Zalo webhook re-enrolment procedure is documented as a runbook and surfaced as an administrator alert, not as a log line.
- [ ] **OPS-03**: The deployment documents plainly that Zalo support requires egress from Vietnam, and states the topology requirement for the region-locked data-residency constraint.
- [ ] **OPS-04**: Runbooks exist for OA refresh-token loss and one-click re-authorisation, Telegram bot-token rotation, and Graph client-secret rotation.
- [ ] **OPS-05**: Runbooks exist for registering each platform's egress IP addresses with the platform.
- [ ] **OPS-06**: The receiver acknowledgement latency is verified at the 99th percentile against the 1.2-second target on every platform, with an alert when it is exceeded.
- [ ] **OPS-07**: The cost of the three-tier rate limiter is measured now that it applies to four platforms, and the directory sync write volume is measured at target tenant size.
- [ ] **OPS-08**: The audit and erasure coverage is re-verified for every identifier introduced in this milestone.
- [ ] **OPS-09**: The outbound delivery failure rate and dead-letter depth are exposed as metrics with alerting.
- [ ] **OPS-10**: The allowlist governance record is updated and each widening is attributable to a named requirement.

## Out of Scope

Explicit exclusions, with reasoning. Listed to prevent scope creep and accidental absorption.

| Feature | Reason |
|---|---|
| Open-ended free-form chat / a general assistant | Contradicts PRD NG1. Free generation produces unverifiable claims, which is a liability in an enterprise HR/ERP context. The guard selects a pre-authorised app; it does not answer. |
| Model tool-calling / function-calling API | Reverses AD-1. The model would become the thing that decides which tools are reachable, making "does this user see the HR app" a model-discretion question. The permission boundary must be unit-testable. |
| Auto-executing a form submission from the AI guard | Bypasses the one-time-link, form-render, and consent model (AD-3, AD-11), and a hallucinated field value would write real data into a downstream ERP. The form is the consent surface. |
| Native IM form rendering (Block Kit, Zalo Mini App forms) | Contradicts NG3 and AD-3. One engine, one renderer, one set of validation semantics. Inline keyboards are for disambiguation choices, not form fields. |
| Zalo Mini App as an alternative entry point | A second form surface and a second identity surface — exactly what NG3 and AD-3 forbid. The OA is the adapter. |
| Long-polling as a Telegram fallback | `getUpdates` and a webhook are mutually exclusive on Telegram — setting one disables the other. A polling fallback breaks the primary path. |
| Zero-staleness group membership | IM platforms expose membership eventually, never instantaneously, and deliver events at-least-once and out of order. Bounded staleness is the honest guarantee. |
| Broadcasting notifications to an entire IM group | Leaks one person's submission status to everyone, breaks FR-N-3's submitter model, and burns the OA's per-user quota on Zalo. Group visibility requires an explicit, audited opt-in. |
| Free-text AI answering questions about downstream data | The platform is not the system of record (NG2). A link retrieves the real data from the source of truth; the assistant does not own it. |
| A second `InboundEvent` schema variant per platform | Destroys the adapter contract — the biggest structural asset of v1. One envelope, `.strict()`, platform payloads translated at the adapter boundary. |
| Real-time multi-user form collaboration | NG4. Out of scope for v1 and v2. |
| Multi-step approval workflow engine | NG5. Out of scope for v1 and v2. |
| Multi-tenant / cross-organisation isolation | NG8. Single enterprise deployment. |
| Mobile-native applications | NG6. Responsive web rendering is sufficient. |
| Re-introducing `passport` / `@nestjs/passport` | Already rejected in v1: it wraps the `jsonwebtoken` that v1 replaced with `jose`. One auth seam across all four platforms. |
| Editing the frozen D-21 / D-23 contracts | They are not edited, they are worked around: the notification TTL is expressed by the issuer, and the AI guard is a provider decorator with zero contract footprint. |

## Notes

- **Frozen contracts stay frozen.** D-21 (read-link claims), D-23 (JEV wire), D-43 (audit field allowlist) are
  worked around, not edited. The audit allowlist widening in AUT-08 is the single deliberate exception, with
  its justification recorded in the same change.
- **New runtime dependencies: 3.** `node-telegram-bot-api@2.1.0` (Telegram client), `ai` + one `@ai-sdk/*`
  provider package (AI guard), and no Zalo package at all. Every rejected alternative carries a documented
  reason (unofficial, unlicensed, deprecated, or the un-instrumented-HTTP-path rule).
- **OpenTelemetry must not be bumped during this milestone.** 3.0.0 shipped 2026-10-20 and is a breaking
  release; it is scheduled as one isolated change afterwards.
- **Four spikes gate the corresponding phases:** S3 (Telegram, Phase 12), S2′ (Zalo, Phase 13),
  S4+S5 (directory sources, Phase 15), S6 (AI provider and model, Phase 16).
