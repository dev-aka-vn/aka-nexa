<objective>
Make routing form-driven, for real. Research proved the CONTEXT's "no routing change" premise
false (07-CONTEXT `<corrections>`): the worker's catalog is one hardcoded demo app
(worker.module.ts:44-70), `RoutingOutcome`/`PublishedApp` carry no action, the slash binding is a
hardcoded two-entry map, and the publish gate enforces **no** form rule at all. This plan lands
the three publish-gate rules (D-05's ≥1-`submit` — NEW, not preserved; APP-12's trigger→form
uniqueness; D-08's routable-kinds), the form-derived tool catalog (one tool per triggered form,
RBAC-filter-before-projection), the de-hardcoded worker wiring, and the one form-driven
issuance seam carrying `form_id`/`form_version`/`action` for every kind (SC#4).

**Flagged assumption (edge-probe row, APP-12 — unclassified, never auto-resolved):** the
spec-less edge probe could not classify APP-12's requirement text. This plan covers APP-12 with
explicit, named checks instead of a probe category: the publish-time uniqueness rule
(`publish-gate.service.spec.ts`), the per-form tool projection (`published-app-loader.spec.ts`),
and the publish→route integration case (`decision-routing.integration.spec.ts`). If the
verifier finds these insufficient, that is a real gap to close — not a silent pass.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| chat user → JEV tool list | Untrusted request text crosses into a permission-filtered catalog |
| published definitions → worker catalog | Stored definitions (possibly un-migrated) cross into routing |
| issuance seam → link URL | Form identity + action cross into a user-visible URL |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-20 | Elevation of Privilege | form-level trigger bypassing app RBAC | high | mitigate | The RBAC filter runs BEFORE the form projection (S8): `listAuthorized` authorizes the app per user first and projects forms only for authorized apps; the loader spec + the integration case (c) assert an excluded user gets zero tools despite triggered forms. The gate additionally rejects triggers on show/edit (D-08), shrinking the routable surface. |
| T-07-21 | Tampering | trigger ambiguity resolved by silent first-wins at routing time | high | mitigate | Publish-time rejection (Task 1 rule 2) is the authoritative control — the ambiguity cannot exist in a published app; the routing-side slash lookup degrades multi-app collisions to the clarify outcome rather than picking. |
| T-07-22 | Tampering | cross-app form injection — issuing against a form the app does not own | high | mitigate | The processor resolves forms only from the authorized list derived from the SAME definition as the app; the loader tolerates un-migrated docs by projecting nothing (fail closed); the tool-id split (`appId:form`) is unambiguous because AppIdSchema forbids ':' and form_id is a kind string. |
| T-07-23 | Tampering | wrong `form_version` in an issued link rendering a stale schema | medium | mitigate | The form_version rides the definition's derived value (D-10, landed 07-01); the integration assertion pins `fv=` to the definition's current per-form version; a mismatch is a red test, not a deploy-time surprise. |
| T-07-24 | Information Disclosure | tool descriptions/labels leaking apps to excluded users | medium | mitigate | Same filter-then-project order (S8): excluded users never see the app's tools or labels; the spec asserts the empty tool list, matching RTE-03's existing guarantee. |
| T-07-SC | Tampering | npm/pip/cargo installs | high | mitigate | Zero packages installed; any discovered need runs the package-legitimacy gate first. |
</threat_model>
